## Comment travailler avec le porteur

- Le porteur n'est pas développeur : lui parler en français, simplement et brièvement, **une action à la fois** pour Neon, Vercel, GitHub, Resend. **Terminer chaque message par « À faire : … »** (ou « rien pour l'instant »).
- Ne jamais lui demander de coller un secret dans la conversation (numéro WhatsApp, clé PostHog, clés API : il les saisit lui-même dans Vercel).
- Ne jamais toucher `MAINTENANCE_MODE`, `public/robots.txt`, `src/generated/prisma/`, `LOT2_OUVERT`, ni un secret. Ne jamais lever la maintenance ni ouvrir l'achat en ligne (Lot 2) dans le code.
- Aucune décision structurante (pile, prestataire de paiement, modèle de données) sans qu'elle soit dans `docs/decisions-porteur.md` ou un document BMAD validé : la poser en question ouverte, avec options lettrées et une recommandation. Le prestataire de paiement (OQ-1) reste ouvert ; ne rien décider dessus.
- Workflow `bmad-build` (skill du dépôt) : spec en `draft` avec questions ouvertes, approbation du porteur (« Approuver et continuer / Approuver et arrêter / Revoir la spec »), implémentation par un sous-agent, relecture par trois sous-agents (aveugle, cas limites, lacunes de vérification), tri des constats dans « Review Triage Log » de la spec (et `deferred-work.md`), corrections, un seul commit propre poussé après relecture (`git reset --soft origin/<branche>` ; les commits « wip » restent locaux ; jamais de force-push). Les retours du hook « commitez et poussez » sont refusés tant que la relecture n'est pas finie.
- Avant de pousser : `npx eslint .`, les trois `node scripts/verifier-exceptions-prisma.cjs origin/main` (nu, puis `tests/exceptions-interface.cjs`, puis `eslint/exceptions-textes.cjs`), `npm test` (PostgreSQL local, `TEST_DATABASE_URL=postgresql://postgres:pg@localhost:5432/postgres` ; ne jamais changer le mot de passe), `npm run test:navigateur` (`NAVIGATEUR_EXECUTABLE=/usr/bin/google-chrome` si besoin), `npm run build`.
- PR : titre « [NE PAS FUSIONNER] … » et brouillon tant que les 4 checks (« Lint et build », « Migrations », « Tests », « Navigateur ») ne sont pas verts sur le dernier commit et que le porteur n'a pas vérifié la préversion ; alors retirer le préfixe, sortir du brouillon, dire « vous pouvez fusionner ». Après la fusion : vérifier la production avec lui, ouvrir une petite PR de suivi (sprint-status → `done`, spec → `done`, entrée du journal dans `docs/migrations.md`).
- Migrations : additives seulement, générées sur une base jetable (`prisma migrate deploy` puis `prisma migrate diff --from-config-datasource --to-schema prisma/schema.prisma --script`, second diff vide avec `--exit-code`). Le porteur les applique lui-même dans l'éditeur SQL de Neon, **avant la fusion** : branche de sauvegarde `sauvegarde-avant-X-Y-AAAA-MM-JJ` créée depuis la production (Neon gratuit limité à 10 branches : supprimer une ancienne sauvegarde si besoin, jamais `production` ni `preview`), puis `preview`, puis production, avec la ligne `_prisma_migrations` et l'empreinte SHA-256 (`sha256sum`). Lui donner le SQL et une requête de contrôle en lecture seule, un bloc à la fois. Jamais `migrate deploy` ni `db push` sur une base partagée.
- Attribution : les commits se terminent par `Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>` et la ligne `Claude-Session: …` de la session en cours ; les descriptions de PR par `🤖 Generated with [Claude Code](https://claude.com/claude-code)` et l'URL de la session.
